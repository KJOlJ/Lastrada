# Web workflow regression checks

The current Firebase description and confirmation flow is documented in
[SAMPLE_DESCRIPTION_FLOW.md](SAMPLE_DESCRIPTION_FLOW.md). The listening and
replay-confirmation flow below describes the retained classic compatibility
tests, not the current interface when connected to the updated API.

For the current `local/stem-fast` Firebase test, use
[STEM_FAST_FIREBASE.md](STEM_FAST_FIREBASE.md). The four-stem measurements below
are historical results from `feat/firebase-web`, not measurements of the new
six-stem profile.

The listening stage checks recording reuse and separate replay/re-singing. A
recording sample does not imply a separate replay. Confirm the recording sample
and its suggested times, and choose **No separate replay or re-sung part** if
that use did not happen. No timestamps or sound details are required for a use
marked absent. At least one use must be present to generate this document.

When Next is blocked, the alert scrolls into view and names the missing decision
or time confirmation. The second rights check keeps its own heading. Status
selects persist on their `change` event, independently of `input` event ordering.
Later stages still require sound/placement details and explicit review before
export. Missing original-track timestamps do not prevent accepting valid
new-track fallback times; unknown source positions remain unknown.

## Automated browser test

```bash
PYTHON=.venv/bin/python npm test --prefix web
```

This tests filename prefill, an unresolved replay check, visible blocking
instructions, change-only select events, unconfirmed timestamps, accepting
recording times, skipping absent replay, sound and placement details, Python
review validation, approved HTML download, and resume after reload.

Google identity, cloud uploads, job transport, and user review actions are
simulated. The Python review and document rendering rules are real. This is not
a live cloud integration test or a human listening review.

To run the same workflow on an already generated private analysis:

```bash
LASTRADA_BROWSER_ANALYSIS=/absolute/private/analysis.json \
LASTRADA_BROWSER_OUTPUT=/absolute/private/browser-output \
PYTHON=.venv/bin/python npm test --prefix web
```

The first path contains an `Analysis` JSON generated by the real pipeline. The
optional second path receives a test-reviewed HTML document and final-screen
screenshot. Keep both paths outside tracked files (for example in ignored
`outputs/private/`). Test-entered descriptions are fixtures, not verified musical
claims. The test still mocks authentication/upload transport and loads the saved
analysis; it does not upload audio to Firebase or rerun detection.

## Deployment for per-moment instruments

This feature changes the API, worker, schema and frontend. A Hosting-only update
is insufficient. The frontend detects an older API and explains that the analysis
service needs updating, rather than applying an old single-region result to all
moments. Existing saved cases remain readable; their single-region stem results
are not treated as per-occurrence evidence. Click the instrument check to add
per-moment results to an existing case.

From the existing Cloud Shell checkout, using the previously selected app/site:

```bash
git switch local/stem-fast
git pull --ff-only origin local/stem-fast
python deploy/bootstrap.py --project lastrada-64bab --expected-branch local/stem-fast --apply --approve-resources \
  --firebase-app-id 1:471058014767:web:2d055ff7689d348fb5dcda \
  --hosting-site lastrada-64bab --confirm-hosting lastrada-64bab/lastrada-64bab \
  --approve-existing-queue projects/lastrada-64bab/locations/us-central1/queues/lastrada-analysis
```

This builds and updates the existing services and Hosting site. Existing billing
and workload limits apply. No larger instances or new service accounts are needed.
Cloud deployment and live inference must be verified separately from local tests.

## Optional per-moment instrument check

The listening screen has one visible **Run instrument check** button. Each row
lists its original/new-track times, estimated sound, and check status. The checked
portion is expandable; a long moment uses a centered probe up to eight seconds
per recording, with one-second margins. A result applies to that checked portion,
not proof of uniform instrumentation across a long interval.

The model estimates bass, drums, vocals and other sounds. Full-mix matches are
not instrument identifications. “Other sounds” remains unidentified. Moments
under two seconds, missing source times, failures and pending checks stay explicit.
A completed comparison can also return no reliable instrument match.

Instrument matching uses stricter 0.5–2x duration ratios than exploratory full-mix
DTW, and a ±2-semitone search. These are candidate suggestions requiring listening
review; they do not determine musical role, lyrics or legal rights.

Checks are opt-in, use the four-stem model and one CPU thread for separation, and
run sequentially. Each request is capped at ten minutes / fifty new comparisons.
Results persist after each moment. Partial runs can continue on request; daily
job quotas still apply. Completed rows and exact separated crops are reused.
Automated timings and previous reviewed document fields are preserved.

Confirmed-time identities link each row to its own evidence. Changing a timestamp
removes that row's prior instrument association. Confirmed timing edits are saved
before a new check, so the worker compares the edited moments. Suggestions fill untouched sound
and method fields; timing suggestions fill repetition and placement. Deliberate
edits, including cleared fields, are retained. Lyrics and role still need creator
input. Prefilled descriptions stay estimated until the listening confirmation.

Run browser scenarios with:

```bash
PYTHON=.venv/bin/python npm run test:instruments --prefix web
```

Generated-data tests cover different instruments at different timestamps,
forward-prefilling, changed timestamps and rechecks, preserved edits and cleared
fields, success/cached results, failures, quotas,
empty results, missing sources and reset during requests. They use mocked cloud
transport and Google identity with real Python review/document validation.

A private real-audio check compared 17 of 50 detected moments; 33 were under the
two-second threshold. Two moments received tentative instrument suggestions;
other checked moments returned no reliable match. The first per-moment pass took
540 seconds on the workspace CPU; reusing the saved results took 0.005 seconds.
These measurements do not establish hosted performance or instrument accuracy.
